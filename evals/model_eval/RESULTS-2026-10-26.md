ranking only (its costs are incomplete). LangSmith experiments are `<config>-<suite>-cb2d0cf-*` and
`<config>-<suite>-20500b1-*`; each records the config SHA-256, the dataset SHA-256 and the git SHA.

Grading is strict. A judged field or answer counts only when **both** LLM judge passes accept it, so
a value one pass accepted and the other rejected is a failure. The failure table in the JSON shows
one pass's reason, so some failures read as acceptable. The same rule applies to every config, so
the figures are lower bounds that are comparable across configs.

## Baseline check

Production on 2026-10-26 serves every extraction on `gpt-5.4-nano` at reasoning `medium`. The
configured primary `google/gemini-3.1-flash-lite` (row `enrichment_default_config`) has returned
402 since 2026-10-23, so the nano fallback serves. The baseline earlier measured on resumes only was
306/312 (98.1%). Here it is 620/624 on resumes (99.4%) and 967/984 overall (98.3%) with invoices, so
the baseline reproduces.

The ranking is the same in both runs. The gap is in invoices: nano at either effort
swaps unit prices and amounts between line items, misses quantities, and adds tax or total rows as
line items (i02, i03, i05, i12, i17). Luna-low extracted every invoice field correctly in all four

payments, `r03.work_experience` one role's dates, extra true locations that one judge pass rejected).

Cost per document is the API's own priced usage for every call on that document, with
`cost_complete: true`. It is not a list-price estimate. Luna-low emits about 249 output tokens per
recorded call, against about 441 for nano-medium, on the same ~1,325 input tokens.

cheaper per answer. The retrieval agent makes more calls with them, so mini costs 2.5x and nano
1.9x what luna costs, and nano's p95 is 47 s.

### Follow-up filter-loss regression (`fu_python_aws_years_chart`)

Turn 1 asks for candidates with Python and AWS and 5+ years (8 people); turn 2 says "chart their
years". The check passes only if the chart covers exactly those 8. Two different failures were
observed in run 2:

- **Filter loss:** chat-mini and chat-nano charted 14 people, which is the population without the turn-1
  filters (extra: Daniel Okafor, Emily Carter, Fatima Sheikh, Michael Brennan, Priya Raghunathan,
  Zoya Ahmed).
- **Dropped member:** the baseline (production chat models) charted 7 of the 8, leaving out Rahul Verma.
  chat-mini did the same once, leaving out Arjun Malhotra.

The baseline passed 2/2 in run 1 and 1/2 in run 2, so the defect reproduces intermittently on the
production chat models. It is a product defect, not a model-selection result.

### Not decided by these runs

These two runs do **not** change production. The selected extraction profile first has to pass a
regression run of `profile-luna-low`, with repeats. That config extracts with luna-low and then
asks all 78 RAG cases on the luna-extracted collections, so a change in extracted metadata cannot
silently move the RAG answers. It runs beside `baseline-nano-medium` in the same workflow run.
Only after it passes do the prod `enrichment_default_config` row and the `openai-v1` default in
`deploy/model-profiles.json` change.
